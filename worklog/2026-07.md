> **THE KNIFE (the cause).** `stripModuleGuard` drops a static ES `import` from an inlined script because its symbols come from a sibling include — but `STATIC_IMPORT` was anchored whole-line (`/^…import…from…;?$/`), so an `import { A, B } from '…'` broken across lines lost only its FIRST line and left the orphaned `} from '…';` tail behind as syntax garbage that kills the ENTIRE `<script>` — silently, no console error, in headless. The fix mirrors the shape the neighbouring `export {…}` / `export default` arms already use: a start/consume pair. `IMPORT_START` (`/^[ \t]*import\b(?![ \t]*[.(])/`) recognizes an import HEAD — the `(?![ \t]*[.(])` lookahead is load-bearing, excluding dynamic `import(` and `import.meta`, and `\b` guards `importantThing`; then it accumulates lines forward until `IMPORT_STATEMENT` (`/^[ \t]*import\b[^'"]*?['"][^'"]*['"][ \t]*;?[ \t]*$/`) matches the terminating module-specifier string. `[^'"]*?` spans newlines (a negated class matches `\n`), so the clause may break across any number of lines, and because everything before the first quote is matched quote-blind a `from` or `{` INSIDE the specifier string can never be mistaken for structure. An import that never terminates now throws a `ForgeError` naming file+line — the silent skip is banned.
