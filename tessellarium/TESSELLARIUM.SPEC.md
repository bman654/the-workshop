# Tessellarium — generative ornament press (the 17 wallpaper symmetry groups)

*A self-contained, zero-dependency, single-file HTML piece for "The Workshop". Placed as
**Strange Garden's companion** — its ornamental cousin: the Garden **grows** pattern (Penrose,
Truchet, WFC, phyllotaxis); the Tessellarium **composes** it, by symmetry law.*

## 0. The crux (workshop tradition — the verifiable gate)

Every wallpaper group is a mathematical object: a discrete symmetry group of the plane, generated by
a known set of operations (translations, point rotations of order 2/3/4/6, mirror reflections, glide
reflections). The whole point of this piece is that the ornament is **provably symmetric** — not a
hand-faked "looks symmetric" pattern, but a field that is **exactly invariant** under its group's
generators.

**The built-in self-test (must PASS, runs headless on load; the Orrery/Ariadne/Blazon-style gate):**

1. **Symmetry invariance.** For the currently-rendered group G, take its generator list
   `gens = [g1, g2, ...]` (each an affine map of the plane in *lattice/continuous* coordinates).
   Sample the **scalar motif field** `f(x,y)` (the pre-rasterization design field — see §3) at many
   random points P inside the fundamental-domain neighbourhood, and assert
   `f(P) ≈ f(g(P))` for every generator g (tolerance ~1e-9, since this is exact arithmetic on the
   field, not pixels). Do this for **all 17 groups**. This proves each pattern truly carries its
   claimed symmetry.
2. **Lattice consistency.** Assert the two translation generators `t1,t2` of each group return the
   field unchanged: `f(P) == f(P + t1) == f(P + t2)` — i.e. it genuinely **tiles** (is doubly
   periodic). Also assert the group's point-group order matches the spec (e.g. p6m has 12 symmetries
   in the point group; p4 has 4; p1 has 1).
3. **Seed reproducibility / style-invariance.** The same seed + same group produces a byte-identical
   field (hash a dense grid of `f` samples). Switching **style/palette must NOT change the field** —
   style only affects colour/stroke/rasterization, never geometry (verify the field-hash is identical
   across all styles for a fixed seed+group). This is the Daedalus/Firmament/Blazon "style only
   re-renders" crux.
4. **Finiteness.** Every sampled `f` value and every transformed coordinate is finite (no NaN/Inf)
   across all 17 groups × several seeds.

Log `PASS`/`FAIL` per check to console and show a small green ✓ chip in the UI (the "self-test: 4/4
✓" badge, workshop convention). **Never ship if any check fails** — fix the construction until it
passes. This is non-negotiable: the crux is the symmetry being *real*.

> **How to make invariance EXACT (this is the key implementation insight):** do NOT generate a motif
> and then "try to" replicate it symmetrically. Instead define `f` as a function that **folds any
> input point back into the fundamental domain by the group action, then evaluates a base motif
> there.** Concretely: `f(P) = motif( foldToFundamentalDomain_G(P) )`. Because `foldToFundamentalDomain_G`
> maps P and g(P) to the *same* canonical representative for any group element g, invariance is true
> **by construction** to floating-point precision. The self-test then merely *confirms* the fold is
> correct. (Equivalent, often simpler: `f(P) = sum over a symmetric orbit of base(P)` where `base` is
> any function and you average/min over the orbit generated by the point group — but the fold approach
> is cleaner and cheaper. Use whichever you can make pass check #1 exactly. The fold is recommended.)

## 1. What it is (the experience)

Seed a coherent, fully-tiled **ornament** — wallpaper in the truest sense. Pick any of the **17
plane symmetry groups** (the complete set; this completeness is part of the charm — show all of
them). A small hand-drawn-feeling **motif** is replicated by the chosen group's exact symmetry
operations into a seamless, infinite, edge-to-edge pattern that fills the canvas. Re-roll endlessly;
every seed a different motif + colourway; export to PNG.

It should feel like William Morris / Islamic girih / Art-Nouveau wallpaper had a baby with a math
toy — *beautiful first, correct underneath.* The viewer should be able to pick "p6m" vs "pgg" and
SEE the difference in the symmetry (6-fold rosettes & mirrors vs. only glides & 2-fold), and a little
caption should name the group + its orbifold signature + a plain-English description.

## 2. The 17 groups (authoritative reference — get these RIGHT)

Use IUC short notation + orbifold + point-group + lattice. The generators below are what the
self-test checks. (All in lattice coordinates where the unit cell is spanned by translation vectors
**a** and **b**; for oblique that's general, for rectangular a⊥b, square |a|=|b| & a⊥b, hexagonal
|a|=|b| & 120° between.)

| IUC | Orbifold | Point group | Lattice | Highest rotation | Mirrors? | Glides? | Plain English |
|---|---|---|---|---|---|---|---|
| **p1** | o | C1 (1) | oblique | none | no | no | only translations |
| **p2** | 2222 | C2 (2) | oblique | 2-fold | no | no | 2-fold pinwheels |
| **pm** | ** | D1 (2) | rectangular | none | yes (parallel) | no | parallel mirror lines |
| **pg** | ×× | (2) | rectangular | none | no | yes (parallel) | parallel glide lines |
| **cm** | *× | D1 (2) | rhombic | none | yes | yes | mirror + parallel glide |
| **pmm** | *2222 | D2 (4) | rectangular | 2-fold | yes (2 dirs) | no | grid of mirrors |
| **pmg** | 22* | D2 (4) | rectangular | 2-fold | yes (1 dir) | yes | mirrors + perpendicular glides |
| **pgg** | 22× | D2 (4) | rectangular | 2-fold | no | yes (2 dirs) | glides only + 2-fold |
| **cmm** | 2*22 | D2 (4) | rhombic | 2-fold | yes (2 dirs) | yes | centred mirrors |
| **p4** | 442 | C4 (4) | square | 4-fold | no | no | 4-fold pinwheels |
| **p4m** | *442 | D4 (8) | square | 4-fold | yes | yes | 4-fold + mirrors (kaleidoscope) |
| **p4g** | 4*2 | D4 (8) | square | 4-fold | yes | yes | 4-fold, offset mirrors |
| **p3** | 333 | C3 (3) | hexagonal | 3-fold | no | no | 3-fold pinwheels |
| **p3m1** | *333 | D3 (6) | hexagonal | 3-fold | yes | yes | 3-fold, mirrors on cell edges |
| **p31m** | 3*3 | D3 (6) | hexagonal | 3-fold | yes | yes | 3-fold, mirrors offset 30° |
| **p6** | 632 | C6 (6) | hexagonal | 6-fold | no | no | 6-fold pinwheels |
| **p6m** | *632 | D6 (12) | hexagonal | 6-fold | yes | yes | 6-fold + full mirrors (rosettes) |

**Point-group orders** (check #2 must match): p1=1, p2=2, pm=2, pg=2, cm=2, pmm=4, pmg=4, pgg=4,
cmm=4, p4=4, p4m=8, p4g=8, p3=3, p3m1=6, p31m=6, p6=6, p6m=12.

**Implementation strategy for the fold (recommended):** for each group, implement
`foldToFundamentalDomain(P)` as: (a) reduce P modulo the translation lattice into the unit cell
(`P -= floor(...)` in lattice coords), then (b) apply the **point-group** folding within the cell:
- rotations: if you're in the "wrong" rotational sector, rotate by −k·(2π/n) about the rotation
  centre until you land in the canonical sector;
- mirrors: reflect across the mirror line if on the wrong side (`x = |x|`-style folds about the
  mirror axes);
- glides: a glide is "reflect + translate by half a lattice vector"; fold by composing the reflection
  with the half-translation and reducing back into the cell.
The canonical representative must be **unique** for the whole orbit — that's what makes invariance
exact. Test it: for random P and random group element g (compose a few generators), `fold(P)` must
equal `fold(g(P))` to ~1e-9. (Glide and the centred/offset-mirror groups — cm, pg, pmg, pgg, cmm,
p4g, p3m1, p31m — are the tricky ones; get the half-translations and mirror placements right. If a
clean fold for the trickier glide groups is hard, the **orbit-min** approach is a robust fallback:
`f(P) = min over g in (a generating set closed to the full point group, expanded over a small
neighbourhood of lattice translations) of base(g·P)` — symmetric by construction because the orbit
set is closed under the group. Whichever passes check #1 exactly.)

> Hexagonal lattice tip: use lattice (oblique 60°/120°) coordinates internally, or work in a skewed
> basis and convert to Cartesian only at raster time. Rotations of order 3/6 are exact about the cell
> origin in that basis.

## 3. The motif (the "base" design field)

`f` ultimately needs to produce something **pretty**, not just a height value. Suggested design:

- The **base motif** `motif(u,v)` over the fundamental domain is a small seeded composition of a few
  smooth primitives: e.g. a sum of a handful of seeded **Gaussian/metaball blobs**, **sinusoidal
  bands**, and **distance-to-a-few-seeded-points** terms, combined into 1–3 scalar "channels". Keep
  it smooth and continuous so the folds don't create hard seams (continuity across fundamental-domain
  boundaries is automatic if `f` is built by folding — the field is genuinely periodic & symmetric).
- Render by sampling `f` per pixel (or per small cell) and mapping the scalar channel(s) through a
  **palette** + optional **contour/iso-line** styling. A few render styles:
  - **Stained**: quantize the field into bands → flat jewel-tone cells with dark "leading" on the
    band boundaries (girih/stained-glass look).
  - **Inked**: smooth palette gradient + thin dark iso-contours (Art-Nouveau line look).
  - **Block**: posterized woodblock-print look (Morris), 3–5 flat colours, slight registration feel.
  - **Line**: white/paper ground, motif as fine contour lines only (blueprint/engraving).
  (4 styles ≈ the workshop norm; pick names you like. Style changes colour/raster ONLY — never the
  field — see crux check #3.)
- The motif must be **seeded** (a small mulberry32/xorshift PRNG; same seed ⇒ same motif). The seed
  is shown and editable (text input + "re-roll" button that picks a new random seed). A URL hash or
  just an on-screen seed is fine; match how sibling pieces (e.g. cartographer/daedalus) expose seeds.

**Important:** make it genuinely attractive across many seeds and all 17 groups. Spend effort on the
palette set (6–8 curated colourways — jewel/Morris/azulejo/Art-Nouveau/ink/monochrome etc.) and on
tasteful leading/contour weights. A boring grey field is a fail even if the math is perfect. Look at
`undercroft/rosette.html` and `compositor/` for the workshop's palette/quality bar.

## 6. Constraints (hard)

- **ONE self-contained file**: `tessellarium/index.html`. Vanilla HTML/CSS/JS. **No frameworks, no
  libraries, no network, no build step.** No external fonts/CDNs (system font stack only).
- Use a `<canvas>` for the pattern. 60fps is trivial here (it's mostly static — render on change, not
  every frame). If you add any animation (e.g. a slow palette shimmer), keep it ≥60fps and
  reduced-motion-safe; static is perfectly fine and probably better.
- **0 console errors/warnings.** Clean.
- Keep the file reasonable (< ~1500 lines ideal; the global rule prefers < 1000 but a single rich
  visual piece can run longer — keep it tidy and commented).
- Relative links only (the site serves from a `/the-workshop/` subpath on GitHub Pages).
- Seed-pure, deterministic. No `Date.now()` feeding the *pattern* (only the breadcrumb timestamp).
